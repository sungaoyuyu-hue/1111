# AI Agent 微信式工作对接 Demo 本地验收清单

本文档用于本地验证和体验验收。验收目标是：员工像使用微信小程序一样，用一句话发起工作对接；系统能理解意图、生成对接事项、匹配协作对象，并模拟公众号/服务通知的即时提醒体验。

## 1. 本地启动验收步骤

### 1.1 启动前检查

- 在工作区根目录确认只进入 demo 目录：

```powershell
cd "C:\Users\Administrator\Documents\New project 8\ai-agent-wechat-demo"
```

- 检查是否存在项目启动文件：

```powershell
Get-ChildItem -Force
```

- 若存在 `package.json`，优先按以下流程启动：

```powershell
npm install
npm run dev
```

- 若项目使用其他栈，以仓库内 README 或启动脚本为准，但验收时必须记录实际启动命令、端口和日志。

### 1.2 启动成功标准

- 终端无阻塞性报错，服务保持运行。
- 浏览器能打开本地地址，例如 `http://localhost:3000`、`http://localhost:5173` 或实际日志输出地址。
- 首屏直接进入可用的工作对接界面，不应是营销落地页。
- 移动端宽度下界面像微信小程序：输入框、发送按钮、消息流、任务状态和提醒卡片均可见。
- 刷新页面后 demo 可恢复到可操作状态，不出现空白页或无限加载。

## 2. 关键用户路径

### 2.1 一句话发起工作对接

1. 员工打开本地 demo。
2. 在输入框输入一句自然语言请求。
3. 点击发送或按回车。
4. 系统识别需求类型、事项标题、紧急程度、候选对接人/部门、建议下一步。
5. 页面生成一张工作对接卡片，并在消息流中给出确认反馈。

验收标准：

- 不要求员工填写复杂表单。
- 输入语义不完整时，系统应追问 1 个最关键问题，而不是失败。
- 生成结果应包含明确的负责人、事项、截止时间或待确认项。

### 2.2 模拟公众号即时提醒

1. 发起对接成功后，右侧或消息流中出现模拟的公众号提醒。
2. 提醒内容包含事项标题、发起人、接收人、优先级和操作入口。
3. 提醒应在 1 秒内出现，或显示清晰的发送中状态。
4. 点击提醒中的查看/处理入口，可定位到对应对接事项。

验收标准：

- 提醒看起来像企业服务通知，而不是普通系统 toast。
- 同一事项的提醒和任务卡片信息一致。
- 失败时有可读的失败原因和重试入口。

### 2.3 对接事项确认与流转

1. 员工确认系统推荐的对接对象。
2. 系统将事项状态从待确认切换为已发起/待响应。
3. 模拟接收人响应后，状态更新为已接单/处理中。
4. 完成后状态更新为已完成，并保留简短记录。

验收标准：

- 状态变化清晰，不依赖用户猜测。
- 关键操作有反馈，不能点击后无变化。
- 历史记录应能说明谁在什么时候做了什么。

### 2.4 异常与边界路径

- 空输入：提示员工输入需求，不创建事项。
- 过短输入：追问补充信息。
- 找不到对接人：给出候选部门或人工分派入口。
- 重复发起：提示可能重复，并允许继续或取消。
- 网络/接口模拟失败：显示失败状态，保留原输入，允许重试。

通过标准：

- 至少 10 条输入均能得到可理解的结果。
- 系统不能把所有请求都映射成同一种模板。
- 对缺失信息的追问应短、准、可回答。
- 公众号模拟提醒内容与事项卡片字段一致。

## 4. UI/交互质量检查点

### 4.1 微信小程序感

- 移动端首屏优先呈现消息流和一句话输入框。
- 输入框固定在底部或始终易触达。
- 发送按钮状态明确：可发送、发送中、不可发送。
- 任务卡片信息密度适中，适合手机阅读。
- 页面不出现明显桌面后台系统风格的复杂表格作为主入口。

### 4.2 即时反馈

- 员工发送后立即看到自己的消息。
- 系统处理超过 500ms 时显示思考中/匹配中状态。
- 成功、失败、待补充、待确认四类状态视觉区分清晰。
- 模拟公众号提醒出现时有轻量动效或明显位置变化。

### 4.3 可读性与可访问性

- 移动端 375px 宽度下文字不溢出按钮或卡片。
- 桌面端不应因为内容过宽导致横向滚动。
- 主要按钮点击区域不小于 40px 高。
- 颜色不能只依赖单一色相表达状态，应配合文字或图标。
- 空状态、加载态、错误态都有明确文案。

### 4.4 工作对接可信度

- 每张事项卡片至少包含：标题、发起人、接收方、状态、优先级、时间信息。
- AI 生成建议应可编辑或可确认，避免直接替员工做不可撤销动作。
- 重要操作例如取消、重新发送、标记完成需要确认或可撤销。
- 历史记录使用业务语言，例如已通知行政、IT 已接单，而不是技术日志。

### 4.5 本地演示稳定性

- 连续发送 10 条测试输入页面不卡死。
- 刷新后仍可继续演示，或清晰说明 demo 数据为临时会话。
- 控制台无持续刷屏错误。
- 未配置真实接口时，模拟数据路径稳定可用。

## 5. 企业微信/公众号/飞书接口留口建议

### 5.1 通用接口边界

建议将前端交互与平台发送能力隔离为统一通知适配层：

```ts
type NotifyChannel = "wechat_mp" | "wecom" | "feishu";

type WorkHandoffNotice = {
  id: string;
  title: string;
  initiatorId: string;
  receiverIds: string[];
  departmentIds?: string[];
  priority: "low" | "normal" | "high" | "urgent";
  status: "pending_confirm" | "sent" | "accepted" | "processing" | "done" | "failed";
  dueAt?: string;
  summary: string;
  actionUrl?: string;
};
```

前端只调用 `sendNotice(channel, payload)`，不要把企业微信、公众号、飞书的 SDK 逻辑散落在页面组件里。

### 5.2 企业微信留口

- 预留 `corpId`、`agentId`、`userId`、`departmentId` 字段。
- 支持按成员、部门、标签发送。
- 预留 OAuth 登录后的员工身份映射。
- 预留审批/待办入口，可将工作对接事项同步到企业微信待办。

### 5.3 微信公众号留口

- 预留 `openId`、模板消息 ID、订阅消息模板 ID。
- 注意公众号消息通常需要用户关注、授权或触发订阅，demo 中应标注为模拟提醒。
- 提醒内容建议抽象为模板变量，例如事项名称、负责人、截止时间、处理入口。
- 预留 `actionUrl`，用于从公众号消息跳回 H5 或小程序页面。

### 5.4 飞书留口

- 预留 `tenantKey`、`openId`、`unionId`、`chatId`。
- 支持发送卡片消息，按钮包括查看事项、接单、转派、标记完成。
- 预留飞书审批、任务或多维表格同步能力。
- 建议将飞书卡片 JSON 模板与业务 payload 分离，方便后续替换样式。

### 5.5 后端与安全建议

- 平台 access token 由后端托管，前端不保存密钥。
- 所有外部回调需要验签、去重和幂等处理。
- 通知发送结果应落库，包含平台、消息 ID、发送状态、失败原因和重试次数。
- 员工身份建议统一映射为内部 `employeeId`，再绑定企业微信、公众号、飞书身份。
- AI 生成的对接建议进入待确认状态，确认后再调用真实平台接口。
